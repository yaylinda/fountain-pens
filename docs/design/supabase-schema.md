# Proposed Supabase relational schema

Status: for Gate A approval, not executable migration SQL. Read [architecture and decisions](client-api-postgres.md) first. This model is a recommendation for a single private owner; public browsing requires a separately reviewed projection/policy before shipping.

## Keys, columns, and relations

Use managed Supabase PostgreSQL at its supported project version; pin the matching local/CI version during implementation rather than requiring PostgreSQL 18 without checking availability. Keep normalized mutable data in `public` with RLS; put administrative configuration/receipts in an unexposed `private` schema. Supabase owns `auth` and `storage`; do not modify their managed table definitions.

Notation: every column below is `NOT NULL` unless marked **nullable**. Every inventory/event ID is nonempty `text`; preserve existing `pen_…`, `ink_…`, and UUID strings. New IDs default to UUID strings. Names/brands are not unique. Do not invent brand/nib taxonomy enums or reject existing unusual nib descriptions.

| Table | Columns and constraints |
| --- | --- |
| `private.collection_owner` | `singleton boolean PK CHECK(singleton = true)`; `user_id uuid UNIQUE FK auth.users(id) ON DELETE RESTRICT`; `time_zone text`. The singleton constraint allows at most one row; setup/import/runtime readiness require exactly one approved account, populated through an authorized administrative operation; timezone validated against PostgreSQL timezone names. Clients cannot change this table. |
| `public.pens` | `id text PK`; `owner_id uuid FK private.collection_owner(user_id) ON DELETE RESTRICT`; `brand text`, `model text`, `color text`, `nib_size text`, `nib_type text`; `archived boolean DEFAULT false`, `favorite boolean DEFAULT false`, `needs_refill boolean DEFAULT false`; common version/timestamps below; `UNIQUE(owner_id,id)`. |
| `public.inks` | `id text PK CHECK(id <> 'NONE')`; `owner_id` as above; `brand text`, `collection text DEFAULT ''`, `name text`; `color_hex text` **nullable**, check `^#[0-9A-Fa-f]{6}$` when present; `archived`, `favorite` default false; common version/timestamps; `UNIQUE(owner_id,id)`. |
| `public.refill_events` | `id text PK`; `owner_id` as above; `pen_id text`; `occurred_on date`; `kind text CHECK(kind IN ('refill','cleaning'))`; `notes text DEFAULT ''`; `not_pure boolean DEFAULT false`; `sequence bigint GENERATED BY DEFAULT AS IDENTITY UNIQUE`; common version/timestamps; `UNIQUE(owner_id,id)`; `(owner_id,pen_id) FK pens(owner_id,id) ON DELETE RESTRICT`; check cleaning implies `not_pure = false`. |
| `public.refill_event_inks` | `owner_id uuid`; `event_id text`; `ink_id text`; `position integer CHECK(position >= 0)`; `PK(event_id,ink_id)`; `UNIQUE(event_id,position)`; `(owner_id,event_id) FK refill_events(owner_id,id) ON DELETE CASCADE`; `(owner_id,ink_id) FK inks(owner_id,id) ON DELETE RESTRICT`. No separate surrogate ID needed. |
| `private.data_imports` | `id text PK` (e.g. `legacy-json-v1`); `owner_id uuid FK collection_owner(user_id)`; `source_sha256 text` (64 lowercase hex); `mapping_version text`; `manifest jsonb` (object containing file hashes, snapshot metadata, counts and validation result); `imported_at timestamptz DEFAULT now()`. Write receipt in the import transaction. Not exposed through Data API. |
| `private.mutation_receipts` | `owner_id uuid FK collection_owner(user_id)`; `request_id uuid`; `command text`; `payload_sha256 text` (64 lowercase hex); `result jsonb` (object); `created_at timestamptz DEFAULT now()`; `PK(owner_id,request_id)`. No browser table access; command functions return only that caller's authorized result. |

Common mutable-record columns: `version bigint DEFAULT 1 CHECK(version > 0)`, `created_at timestamptz DEFAULT now()`, `updated_at timestamptz DEFAULT now()`. Return versions in a JS-safe representation as well as ordering sequence. Only trusted database code sets/increments these columns. Updates increment version exactly once; no-op behavior should be documented and tested. Never infer historical creation times from the event date: imported timestamps describe import, not when the owner originally wrote the entry.

Map missing optional legacy booleans to false, absent custom colors to NULL; required source text stays exactly as supplied, including accents and notes. Source text must be inspected before imposing additional nonblank/length checks. At Gate A select bounds that accept audited legitimate rows, then apply equivalent DTO and SQL checks. Do not globally trim/rewrite historical strings or treat unknown catalog facts as false.

Create indexes for the actual access paths:

- `refill_events(owner_id, pen_id, occurred_on DESC, sequence DESC)` for current pairing and pen history.
- `refill_events(owner_id, occurred_on DESC, sequence DESC)` for ordered journal reads.
- `refill_event_inks(owner_id, ink_id, event_id)` for ink history and FK lookups.
- Unique `(owner_id,id)` inventory/event indexes support composite FKs and owner filtering. Join PK/unique indexes support ordered event links. Add no speculative full-text/materialized aggregate tables.

Deletion is deliberately restrictive: referenced pens/inks cannot be hard-deleted; archive them while retaining journal history. Deleting an event removes its own links only. Deleting the Auth owner is blocked pending an explicit data-retention operation. Owner changes are not normal mutations.

## Journal identity and history semantics

An event ID identifies a journal entry permanently. `sequence` orders ties; it is not a mutable row number or a date. Import sequence follows **actual source array order**, ignoring embedded legacy `index`. Edits keep ID and sequence; deletes leave gaps; new events get higher sequences. Exact repeated JSON entries remain distinct events. No uniqueness constraint on pen/date/payload and no content-based deduplication.

Latest pairing is the event with `occurred_on <= asOf`, ordered by date DESC then sequence DESC. A cleaning means empty; no event means empty. Archived pens remain in history but leave active desk/queue views. Pen refill counts exclude cleanings; each mixture contributes once to each referenced ink's history. Existing history/count selectors include stored future rows while current pairing excludes them; importer parity must not silently change this if fresh input contains future rows.

Cleaning has zero ink links and false `not_pure`. Refill has at least one distinct link; positions form a contiguous zero-based ordered list. `not_pure` denotes residual ink and is independent of mixture size. Preserve both. The `NONE` row is a legacy UI sentinel, never an inventory record in PostgreSQL.

Ordinary SQL CHECK constraints cannot inspect another table. Implement a deferred constraint trigger on event/link changes that checks final event kind, link cardinality, and contiguous positions at transaction end (skip a deleted parent). Cover direct privileged import writes as well as RPC writes. Serialize command edits to a given event so two link replacements cannot interleave. FK/unique/row checks still run independently. [PostgreSQL constraint guidance](https://www.postgresql.org/docs/current/ddl-constraints.html) explains the cross-row CHECK limitation.

`needs_refill` is current queue intent on the pen. Only **creating a new latest eligible event** changes it automatically: a refill clears it; cleaning accepts an optional explicit queue choice, otherwise retains the current value. Backdated creation that does not become latest, all event edits (including pen/date changes), and all event deletes leave queue intent unchanged. Explicit pen mutation can always change it. A same-day appended event wins. Decide eligibility using the locked database state and approved timezone, not a stale browser selector. Do not replay historical events to recompute the imported flag.

The journal stores the current version of each historical fill/cleaning entry, matching today's editable journal. It is **not an immutable audit of every correction/deletion**. Optimistic versions and request receipts do not supply audit history. If revision history is desired, approve a separate append-only audit table/retention policy before migration; do not imply it already exists.

## Transactional command boundary

Recommend no direct client INSERT/UPDATE/DELETE grants on domain tables. Client reads use RLS; mutations use individually granted RPCs. Expose thin `public` SECURITY INVOKER RPC wrappers that call narrowly scoped `private` SECURITY DEFINER mutation functions. Keep the definer functions outside Data API exposed schemas. The private functions own the transaction while direct DML is revoked; invoker-only DML functions would fail without table grants. Use a dedicated non-login, non-superuser role without BYPASSRLS, minimal table/sequence privileges, explicit policies for that role, and table ownership elsewhere. Do not default to a powerful `postgres`-owned mutation function. Enable/force RLS where appropriate for domain table ownership; verify actual role behavior in tests.

Every definer function must explicitly verify `auth.uid()` matches the one approved owner; fix `search_path = ''`; fully qualify objects; reject client owner IDs; restrict argument fields; avoid caller-controlled dynamic SQL. Revoke default EXECUTE from PUBLIC/anon/authenticated (including future-function default privileges). Grant `authenticated` EXECUTE on the named public wrappers and only their exact private mutation functions, plus private schema USAGE needed to call them; grant no private table access. The private implementations must be safe even if invoked directly through SQL with those privileges: the wrapper is not an authorization boundary. Revoke schema CREATE privileges from untrusted roles. A narrowly scoped private owner-check helper may read owner configuration, returning only whether the current identity matches; grant only what the policies need. Test its search path and inability to enumerate/change configuration. [Supabase function security guidance](https://supabase.com/docs/guides/database/functions).

For this small collection, serialize all mutations and final import with the **same transaction-level advisory lock for the collection**. This simple strategy gives queue decisions, inventory version updates, event edits/deletes, and receipt replays one consistent order. Acquire the lock before reading relevant rows or allocating ordering sequence. Lock/version-check target rows; perform event/link/pen changes; enforce deferred constraints; store the response receipt; commit atomically. A later concurrency optimization must retain the same invariants.

For each request, compute the payload digest in trusted code over a documented canonical command representation. Existing `(owner,requestId)` with the same command/digest returns its committed result; reuse with a different payload is a conflict. Receipt creation shares the transaction, so failure leaves neither partial data nor a false success receipt. Retain receipts through the supported retry lifetime; recommended initial policy is no automated deletion at this scale. Gate any later pruning with a defined idempotency expiry contract. Replays may return an older committed result; client refresh then obtains current state.

Version-guard updates/deletes atomically (`WHERE id = ... AND owner_id = ... AND version = expectedVersion`) and require exactly one matching row. Pen queue effects increment that pen's version only when its flag changes. Missing/foreign records and stale versions produce safe adapter errors, without leaking another owner's data. The owner-scoped read RPC can remain SECURITY INVOKER with SELECT grants. A separate narrowly granted private definer helper returns only the authenticated owner's timezone/asOf and edit capability after checking the allowlist; it does not expose the configuration table. This supplies read context without giving invoker reads private table privileges. Compute the local date from database time in that approved timezone, return it with the collection, and refresh on local day rollover/reconnect; never trust a browser-provided asOf to authorize a write. Prefer invoker views or no exposed views; default privileged views can bypass RLS.

## Authorization and secrets

Enable RLS on every exposed domain table, including junction/media tables. Revoke inherited/default privileges then grant SELECT only where required. Policies require both `auth.uid() = owner_id` and membership in the one-owner allowlist. RLS for the mutation role must have the same owner restriction and WITH CHECK for inserted/updated rows. Grant that role the necessary SELECT privileges and SELECT policies as well as UPDATE privileges/policies: version-guarded updates must be able to read their target rows. Browser roles retain SELECT only and cannot use direct DML. Composite FKs prevent cross-owner references even if a policy is later changed. Owner IDs are assigned in commands and immutable.

| Caller | Collection read | Direct domain DML | Command RPC | Private media |
| --- | --- | --- | --- | --- |
| Signed out (`anon`) | Denied by default | Denied | Denied | Denied |
| Authenticated non-owner (including anonymous Auth user) | Denied | Denied | Denied inside function | Denied |
| Approved owner | Allowed by RLS | Denied | Allowed with validation/version checks | Allowed by bucket/path policy |
| Authorized migration operator | Explicit controlled connection only | Import transaction with reconciliation | Not a web session | Separate explicit transfer, if needed |

RLS protects database rows and grants limit available operations; both must be set and tested. Do not grant every authenticated user access or rely on UI hiding. [Supabase RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security). If anonymous browsing is approved, define a minimal read projection and its policy separately; ensure notes, owner identifiers, receipts, and private object paths are excluded unless intentionally public. Public reads never imply public writes.

The browser receives only `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`; these are public build inputs. Auth supplies the user's JWT. Database passwords, Supabase secret/service-role keys, management tokens, Vercel tokens, and legacy Git/Vault credentials must never enter `VITE_*`, bundles, URLs, source control, or logs. Secret/service-role credentials bypass RLS and are not needed for routine browser CRUD. [Supabase API-key guidance](https://supabase.com/docs/guides/getting-started/api-keys).

## Catalogs and media

Keep `src/data/pilot-inks.json`, `src/data/wearingeul-inks.json`, and `scripts/output.json` (plus its CSV/provenance) as versioned **reference** data initially. They are not mutable inventory tables and their unknown/null fields are not missing user input. Preserve brand+ink-ID associations, source URLs, Japanese names/readings, notes, and retrieval metadata. No catalog rows should recreate deleted inventory. Keep custom database color → manufacturer reference RGB → approximate generated swatch → unknown precedence. The current generated fallback keys by name; changing reconciliation keys is separate work.

Current data has no collection photo field and tracked assets are fonts/logos, so there is **no known user-media backfill**. Audit live files before claiming otherwise. Supabase Storage is the chosen destination for future uploaded media; static application assets remain in Vercel's build. Do not add image editing/upload UI solely for this migration.

If media is approved for the first release, add `public.media_assets` in its own reviewed migration: `id uuid PK`, `owner_id` owner FK, `bucket_id text`, `object_path text`, `mime_type text`, `byte_size bigint CHECK(byte_size >= 0)`, `sha256 text` nullable, `alt_text text DEFAULT ''`, `pen_id text` nullable, `ink_id text` nullable, `event_id text` nullable, common version/timestamps, and `UNIQUE(bucket_id,object_path)`. Require exactly one target with `num_nonnulls(pen_id,ink_id,event_id)=1`; each `(owner_id,target_id)` has the corresponding composite FK ON DELETE RESTRICT. Index each non-null target FK. An event/ink/pen with attachments requires explicit media cleanup before deletion. Do not store signed URLs or image blobs in these rows.

Use a private `collection-media` bucket and immutable paths `<owner-uuid>/<asset-uuid>/<filename>`. `storage.objects` SELECT/INSERT/UPDATE/DELETE policies must require that bucket, authenticated approved owner, and matching first path segment; UPDATE needs both USING and WITH CHECK. Do not rely solely on Storage's uploader owner metadata, which differs for service uploads. Disable overwrite/upsert initially; bound MIME types and size at the bucket and client. Use authenticated download or short-lived signed URLs; a signed URL grants access until expiry and must not be treated as permanent private identity. [Storage access controls](https://supabase.com/docs/guides/storage/security/access-control).

Object upload and PostgreSQL metadata are not one ACID transaction. Upload first to a unique authorized path, register/link metadata with an owner command after successful upload, and compensate or reconcile unlinked objects after failure. For deletion, use an explicit pending-delete/retry workflow or operator reconciliation so metadata is not silently considered authoritative when object deletion failed. Never delete from `storage.objects` directly as an object-removal substitute. Before adding uploads, approve this lifecycle and tests; otherwise defer the media table/bucket provisioning and keep this as the storage contract.
